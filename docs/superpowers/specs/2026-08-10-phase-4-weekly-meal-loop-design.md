# Phase 4 Weekly Meal Loop Design

日期：2026-08-10
状态：用户已批准
阶段：阶段四“一周餐单与联动闭环”

## 1. 目标

在当前 `feat/v1.0` 主线上完成从每日营养目标到可执行一周餐单的纵向闭环：用户以标准食材名称和克数维护库存，系统只使用经过运行时校验的审核营养快照与食谱模板，确定性生成七天餐单；训练计划或实际完成度变化后，只重算受影响的未来日期，并保证锁定或手动修改过的餐单不会被后台静默覆盖。

阶段四完成后，用户应能在微信原生小程序中完成以下流程：

1. 查看当前身体档案、目标、训练计划和每日营养目标。
2. 手动录入一组现有食材和可用克数。
3. 生成七天完整餐单并查看每餐食谱、实际食材克数和复算营养。
4. 按天锁定餐单，或通过结构化表单手动修改某餐。
5. 移动、取消或改变未来训练后查看餐单联动结果。
6. 对锁定日的目标差异选择保留旧餐单或明确覆盖。
7. 记录实际训练分钟数，并让可重算的当日目标与餐单同步变化。

## 2. 范围与非目标

### 2.1 本阶段范围

- 手动食材库存的不可变版本。
- 审核每日菜单目录和确定性七天餐单生成器。
- 一周餐单不可变版本、活动指针和待确认候选。
- 按天锁定、结构化手动修改和自动锁定。
- `TrainingPlanChanged` 幂等消费和餐单重算。
- 实际训练完成分钟事件及其当日影响。
- CloudBase 聚合 schema v3 到 v4 的结构迁移。
- planning API、微信小程序餐单/执行页面及本地端到端验收。

### 2.2 本阶段非目标

- 食材图片上传、视觉识别和图片清理，留到阶段五。
- LangGraph、LLM 意图识别和对话修改，留到阶段六。
- 实时付费营养 API、生产营养数据导入和商业授权验收。
- 疾病、孕期、未成年人、康复、医疗建议或范围外个性化热量。
- 体重趋势自动扩大热量盈亏；MVP 仍禁止自动扩大调整。
- 任意菜谱创作、任意 URL、客户端提供的工具名或模型产生克数。

## 3. 方案选择

采用当前单一规划聚合内扩展的方案，不创建新聚合、分支、工作区、框架或依赖。

选择理由：

- 当前身体档案、目标、训练计划、每日能量/营养目标和 outbox 已在同一用户聚合内以事务方式写入。
- 阶段四的核心风险是版本引用、锁定保护、事件幂等和失败回滚；同一聚合能在 CloudBase 单文档事务边界内证明这些不变量。
- 独立餐单聚合会引入跨聚合 Saga、补偿和额外运维，不符合当前单人 MVP 的维护优先级。
- `phase1-local` 只作为审计来源。其代码耦合旧 schema、后续 Agent 和 Provider，不整体合并或据此勾选进度。

## 4. 架构与职责

依赖方向保持不变：

```text
微信小程序餐单/执行页
  → planning-api 运行时契约与可信身份
    → 库存、餐单、完成度和重算应用服务
      → 版本化领域模型与纯 TypeScript 生成/校验
        → NutritionProvider、RecipeTemplateProvider、DailyMenuCatalogProvider
          → 本地审核缓存或 CloudBase 适配器
```

### 4.1 `domain`

定义库存、每日菜单目录、餐单、锁定、目标差异、用户决定、完成度事件和重算任务的不可变类型。领域层不导入 CloudBase、模型 SDK 或供应商 DTO。

### 4.2 `calculation`

实现无网络、无数据库、可重复执行的 `generateWeeklyMealPlan` 和餐单日校验。所有份量、食材克数、营养汇总和候选排序都由确定性 TypeScript 产生。

### 4.3 `application`

实现库存保存、首次生成、餐单手改/锁定、训练完成度记录、事件消费、候选决定和当前上下文查询。Provider 数据在事务外加载并冻结，事务内重新检查活动版本后才写入。

### 4.4 `providers`

对营养快照、食谱模板和每日菜单目录做运行时 schema 校验、质量状态门禁和字段映射。生产模式拒绝 `test_fixture`。

### 4.5 `persistence`

验证 schema v4 和跨版本引用不变量，以用户可信身份限定单文档读写。v3 文档只结构性补充空的阶段四集合与空指针，不推断历史库存、餐单或完成度。

## 5. 领域模型

### 5.1 库存版本

`InventoryVersion` 是整份库存快照，而不是对单个食材原地增减：

```ts
interface InventoryVersion {
  kind: 'inventory_version';
  id: string;
  userId: string;
  version: number;
  createdAt: string;
  items: readonly {
    foodId: string;
    nutritionSnapshotId: string;
    availableGrams: number;
  }[];
}
```

同一快照内 `foodId` 唯一，`availableGrams` 使用统一克单位且必须为正数。用户输入普通中文名称；服务端只在固定审核数据集中做规范化精确匹配，返回明确候选或未找到，不做模糊模型推断。保存时固定对应的营养快照 ID，后续供应商数据变化不改变历史库存含义。

### 5.2 每日菜单目录

`DailyMenuTemplateVersion` 引用若干不可变食谱模板并指定餐次。`DailyMenuCatalogVersion` 是生成器可用的固定菜单清单，包含 `sourceId`、`datasetVersion`、`reviewedAt` 和 `qualityStatus`。应用服务只读取配置指定的活动目录，不接受客户端提供目录或模板 ID。

### 5.3 餐单版本

`MealPlanVersion` 至少包含：

- `id`、`userId`、`version`、`createdAt`、`weekStartDate`。
- `bodyProfileVersionId`、`goalVersionId`、`trainingPlanVersionId`。
- `inventoryVersionId`、目录版本、生成策略版本和来源 ID。
- `supersedesVersionId`，首版除外。
- 七个 `MealPlanDay`；目标周期或适用范围导致不足七个可规划日期时，返回明确不可行结果，不创建伪造空日。

每个 `MealPlanDay` 包含：

- 业务日期和精确 `dailyNutritionTargetVersionId`。
- `locked` 与 `manuallyModified`。
- 餐次、食谱模板版本和确定性份量倍数。
- 每种食材的实际克数。
- 从每 100 克快照复算的 `NutrientValues`。
- 使用过的营养快照 ID、食谱版本 ID 和菜单模板版本 ID。

活动餐单由 `activeMealPlanVersionId` 指针决定。候选本身不可变；未完成、待确认或失败候选不能成为活动餐单。

### 5.4 按天锁定与手动修改

- 用户可主动锁定或解锁未来日期。
- 结构化手动修改成功后，该日自动设置 `manuallyModified: true` 和 `locked: true`。
- 手动修改仍须满足来源、过敏原、忌口、库存和营养校验；失败时不创建新版本。
- 解锁通过餐单后继版本表达，只影响后续重算，不改写旧版本。
- 训练变化不得静默替换锁定或手动修改日。

### 5.5 训练完成度与重算记录

`TrainingCompletionEvent` 保存活动训练计划版本、业务日期、实际完成分钟数和发生时间。实际分钟必须在 `0–300`，日期不得晚于当前业务日，且必须对应活动周内的已计划训练。

`MealPlanTargetDiff` 保存锁定日的旧/新营养目标版本和结构化差异原因。`MealPlanDecision` 保存用户选择：

- `keep_existing`：活动旧餐单保持不变，并记录用户知悉其与当前目标不同。
- `overwrite_locked`：允许生成新的完整候选；成功后原子激活。

`RecalculationJob` 以触发事件 ID 为幂等边界，记录受影响日期、状态和结果版本 ID。状态可以是 `pending`、`completed` 或 `failed_retryable`；业务事实事件本身不因处理状态而改写。

## 6. 确定性生成策略

策略名为 `weekly-meal-generation-v1`，来源至少包含 `CNS-DIETARY-GUIDELINES-2022`、活动 `nutrition-policy-v1` 的来源以及每条食谱/营养快照自身来源。

### 6.1 输入

- 活动身体档案中的过敏原、忌口和饮食偏好。
- 七个每日营养目标版本。
- 活动库存版本。
- 固定每日菜单目录及其引用的食谱和营养快照。
- `allowTestFixtures`，只在测试/本地模式为 `true`。

### 6.2 硬过滤

候选依次执行以下硬门禁，任何一项失败都不降级：

1. 菜单、食谱和营养快照的 schema 与质量状态有效。
2. 食谱食材 ID 与固定营养快照身份一致。
3. 食材不包含用户过敏原，不命中忌口。
4. 整周累计食材克数不超过库存。
5. 每日营养落在活动目标和 `meal-plan-validation-v1` 的容差内。
6. 每日至少 12 个不同食材、至少 5 个核心食物组；一周至少 25 个不同食材。油脂和 `other` 不计入核心食物组。

上述多样性常量集中在 `food-diversity-policy-v1`，来源为《中国居民膳食指南（2022）》。改变常量必须增加策略版本，不修改历史餐单。

`meal-plan-validation-v1` 固定使用能量相对误差不超过 `10%`、蛋白质相对误差不超过 `10%`；脂肪 `20%–30%E`、碳水 `50%–65%E` 且至少 `120 g`、纤维 `25–30 g`、饱和脂肪 `<10%E`、添加糖 `<10%E` 继续使用 `nutrition-policy-v1` 的严格边界。过敏原、忌口、来源、库存和多样性没有容差。

### 6.3 份量和排序

- 菜单整体份量倍数只从 `0.50` 到 `1.50`、步长 `0.05` 的固定网格选择。
- 所有食材克数从模板克数乘倍数后按统一半入规则取一位小数。
- 营养汇总始终从实际克数和每 100 克快照重新计算，不信任供应商汇总文本。
- 候选先按硬约束过滤，再按能量相对偏差、蛋白质相对偏差、食物重复度、菜单版本 ID 的稳定顺序排序。
- 相同输入、策略和数据版本必须得到字节级等价的业务结果。

### 6.4 原子结果

生成器返回完整七天结果，或：

```ts
{
  kind: 'infeasible';
  code: 'nutrition_constraints_infeasible';
  conflicts: readonly WeeklyMealConflict[];
}
```

冲突必须包含日期和稳定代码，例如目标不可行、来源缺失、过敏原、忌口、库存不足、营养超界或多样性不足。任何一天失败都不保存部分餐单。

## 7. 命令与数据流

所有写命令使用服务端可信 `userId`、`expectedVersion` 和 `idempotencyKey`。客户端不得提交可信身份、MET、营养汇总、来源状态或活动指针。

### 7.1 保存库存 `saveInventory`

1. 运行时校验中文名称和克数。
2. 从固定审核数据解析标准食材与营养快照。
3. 合并规范化后重复食材，拒绝无匹配、非正数和不可靠来源。
4. 在事务内重查预期版本并追加完整 `InventoryVersion`。
5. 旧库存版本保留；已有餐单不被后台自动改写。

### 7.2 首次生成 `generateWeeklyMealPlan`

1. 读取活动版本链和七天目标。
2. 在事务外加载固定目录及所有引用记录并做 schema 校验。
3. 运行纯生成器。
4. 在事务内重新检查身体档案、目标、训练计划、库存和目标版本均未变化。
5. 一次追加完整 `MealPlanVersion` 并切换活动指针。

### 7.3 训练计划变化与 `TrainingPlanChanged`

1. 现有保存命令原子追加训练计划、受影响日期的新能量/营养目标和 pending outbox 事件。
2. API 保存成功后立即尝试幂等消费；失败不撤销已保存的用户训练选择，事件保持可重试。
3. 消费端只处理事件的未来 `affectedDates`。无关日期复用原餐单日及其历史来源证据。
4. 未锁定日期重新生成或在新目标下重新验证后复用。
5. 没有保护日且完整候选成功时，原子激活新餐单并完成任务。
6. 存在保护日时，活动旧餐单继续可读并标记 `stale: true`，保存完整候选、差异和待确认任务，不切换活动餐单。
7. `keep_existing` 完成该任务并保留 stale 活动餐单；`overwrite_locked` 只有在完整新版本成功后才切换活动指针。

### 7.4 实际完成度 `recordTrainingCompletion`

1. 总是先以幂等命令保存事实事件。
2. 日期早于当前业务日时，只记录事实，不创建新目标或餐单。
3. 日期为当前业务日时，只用实际分钟重算该训练日；`0` 表示取消完成。未来日期不是已发生事实，命令必须拒绝。
4. 创建引用完成度事件的新能量/营养目标版本，再走同一餐单重算流程。
5. 餐单 Provider 或生成失败不能导致完成度事实丢失；重算任务保持可重试。

### 7.5 锁定 `setMealPlanDayLock`

只允许活动周内不早于当前业务日的日期。命令创建完整餐单后继版本，仅改变目标日锁定状态，并原子切换活动指针。

### 7.6 手动修改 `updateMealPlanDay`

客户端提交日期、餐次和从服务端列表选择的食谱版本，不提交克数或营养汇总。服务端确定性选择份量、复算整周库存和营养，并校验全部硬约束；成功后创建活动后继版本并自动锁定该日。

## 8. API 与小程序

planning API 新增或扩展以下动作：

- `resolveFoodName`
- `saveInventory`
- `generateWeeklyMealPlan`
- `setMealPlanDayLock`
- `updateMealPlanDay`
- `recordTrainingCompletion`
- `decideMealPlanCandidate`
- `retryPendingRecalculation`
- `getCurrentPlanningContext` 返回活动/过期餐单、待确认候选、差异和最新版本计数。

错误码保持稳定：`invalid_request`、`version_conflict`、`provider_unavailable`、`nutrition_constraints_infeasible`、`past_fact_immutable` 和 `candidate_not_pending`。响应不包含 `userId`、内部日志、签名 URL 或敏感供应商正文。

微信小程序新增“一周餐单与执行”页面，并从现有规划页面进入。页面提供：

- 多行中文食材名称与克数录入，逐行解析状态。
- 七天餐单、餐次、菜名、食材克数和估算营养展示。
- 每日锁定开关和结构化换菜表单。
- stale 提示、旧/新目标差异及保留/覆盖选择。
- 实际训练分钟录入；事实保存结果与餐单重算结果分开展示。
- 过敏原、库存、来源和无解冲突的中文可操作提示。

页面不要求用户键入内部食材、食谱、目标或版本 ID。内部 ID 只存在于服务端返回的受控选择项和隐藏请求状态。

## 9. 持久化与迁移

`PlanningAggregateState` 增加：

- `inventories`
- `mealPlans`
- `mealPlanTargetDiffs`
- `mealPlanDecisions`
- `trainingCompletionEvents`
- `recalculationJobs`
- `activeInventoryVersionId`
- `activeMealPlanVersionId`
- 对应幂等记录与最新版本计数

CloudBase 写入 schema v4。读取 schema v3 时仅补上述空数组和空指针，然后执行与 v4 相同的语义不变量验证。迁移不得制造历史库存、餐单、完成度、决定或已处理事件。

持久化不变量至少验证：

- 所有私有记录属于可信用户。
- 版本连续、ID 唯一、活动指针存在。
- 餐单引用的身体档案、目标、训练计划、库存和营养目标均存在且属于同一版本链。
- 每个餐单日日期唯一并属于对应周。
- 每日营养目标与餐单日引用的训练计划一致。
- 差异、决定和重算任务引用存在的事件/餐单/目标。
- 已激活餐单是完整七天、没有 `needs_generation` 或未解决保护差异。

## 10. 并发、幂等与失败处理

- 命令指纹继续使用规范化 `v2:sha256`，相同键不同载荷返回幂等冲突。
- outbox 消费以 `eventId` 唯一；重复消费不能生成多个有效餐单或目标版本。
- Provider 数据在事务外加载；事务内对所有输入版本做 compare-and-set。变化时返回 `version_conflict`，不使用过时快照提交。
- Provider 超时、schema 失败、目录缺失或约束无解时，旧活动餐单继续有效；任务记录可重试状态，不写入部分活动候选。
- 新候选完整成功前不失效旧餐单。
- 过敏原、健康范围、来源链和库存永不因失败自动放宽。
- 日志只记录匿名用户标识、事件/请求 ID、延迟、状态和稳定错误码，不记录完整身体档案、自由文本库存、供应商正文或营养快照内容。

## 11. 测试策略

所有行为按 RED → GREEN → REFACTOR 实现。

### 11.1 计算层

- 每 100 克数据与实际克数的半入复算。
- 固定份量网格、稳定排序和相同输入确定性。
- 整周累计库存守恒，不能跨日重复使用克数。
- 每日/整周多样性边界。
- 营养目标容差、来源缺失和 unsupported 目标。
- 对所有过敏原子集与候选排列做属性测试，证明接受结果从不含冲突食材。

### 11.2 应用与领域层

- 库存版本、活动指针、普通名称解析和幂等重放。
- 完整七天生成、任一天失败无部分写入。
- 按天锁定、自动锁定、解锁和手改失败回滚。
- 训练移动、取消、增加/减少时长只影响正确未来日期。
- 实际完成分钟降低只影响当日，过去日期只追加事实。
- locked 候选的保留/覆盖决定、重复决定和错误候选状态。
- 重算事件重复、Provider 失败重试、版本冲突和完整成功后激活。
- 只移动训练日时整周训练净消耗守恒；无关餐单日不产生新内容。

### 11.3 持久化、API 与客户端
