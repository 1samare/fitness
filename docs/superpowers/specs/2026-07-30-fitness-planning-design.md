# Fitness 目标驱动训练与饮食规划设计

日期：2026-07-30  
状态：用户已确认，计算策略经科学审阅后更新为 `calculation-policy-v2`  
目标：确定 MVP 的产品边界、系统架构、数据策略和不可违反的约束。

## 1. 背景与目标

项目面向中国大陆健康成年人，以微信小程序交付。用户先提供身体数据和偏好，再设定健身目标、制定一周训练计划。系统依据每日训练负荷计算营养目标，并结合用户现有食材推荐食谱与克数。训练计划或实际完成度变化时，系统对受影响的未来日期重新规划饮食。

成功标准不是一次生成一份看似合理的菜单，而是建立可追溯、可修正、数值一致的“目标—训练—饮食—执行”闭环。

## 2. 已确认需求

- 目标人群：中国大陆健康成年人。
- 交付平台：微信小程序。
- 团队形态：个人借助 Codex 开发，优先方便和低运维。
- 基础设施：接受微信云开发/腾讯 CloudBase，不自建服务器。
- 预算：MVP 不设硬性费用上限，优先便利、可靠和数据质量。
- 模型：中国大陆供应商优先。
- 计划周期：一周，可按天调整。
- 输入：身体数据、结构化训练计划、手动食材和食材照片。
- 识图范围：只识别现有食材，不识别训练计划。
- 交互：生成计划后支持有限对话修改。
- 执行反馈：用户确认训练完成度，系统据此修正后续推荐。
- 精度：热量消耗允许近似，不宣称医疗级精度。
- 自动能量目标范围：18–45 岁、BMI `18.5–<24.0`、完成最小化健康排除项确认且输入完整的用户。
- 范围外行为：仍可提供食材管理和一般均衡食谱，不提供自动减脂或增肌热量。

## 3. 方案选择

选择 LangGraph.js + CloudBase Serverless：

- 小程序和后端统一使用 TypeScript，降低个人开发的上下文切换。
- CloudBase 提供微信身份、数据库、存储、云函数和 AI 接入，不需要服务器运维。
- LangGraph 把对话理解和确定性业务流程连接起来，同时保持代码可测试、可版本化。
- 不采用多 Agent；当前问题是受控工作流和状态一致性问题，不需要自治协作。
- 不用 Dify 作为核心编排，以避免额外部署、平台配置漂移和复杂领域逻辑难以测试。
- 不用腾讯 ADP 作为 MVP 主平台；其企业工作流和运营能力可在规模化阶段重新评估。

## 4. 组件设计

### 4.1 微信小程序

负责登录、结构化录入、计划展示、差异确认、图片上传和有限对话 UI。客户端不持有供应商密钥，不执行可信营养计算，不直接写入任意模型输出。

### 4.2 云函数/API 层

验证用户身份、DTO、版本号和幂等键，调用应用服务并转换错误。所有第三方 API 从服务端调用。

### 4.3 LangGraph 编排层

识别用户意图、收集必要参数、选择白名单工具、协调重算和解释结果。状态图不拥有营养事实，不直接写数据库。

### 4.4 领域与计算层

保存目标、训练、饮食之间的规则，完成能量估算、营养目标、影响范围和食谱约束验证。该层不依赖模型或供应商 SDK。

### 4.5 数据与知识层

CloudBase 文档数据库保存高频、结构化、用户相关的事实；CloudBase 知识库保存低频的指南和解释性内容。营养数据同时保存内部标准模型、供应商来源和审核状态。

### 4.6 Provider 层

以 `VisionProvider`、`NutritionProvider`、`LanguageModelProvider` 和 `KnowledgeRetriever` 隔离供应商。首选混元文本/视觉模型和 TianAPI 营养接口，但领域代码不感知供应商字段。

## 5. 核心数据流

### 5.1 首次规划

1. 保存身体档案和安全偏好版本。
2. 保存目标及目标周期。
3. 保存一周训练计划版本。
4. 计算基础消耗、每日训练净消耗和目标能量。
5. 计算每日宏量营养素目标。
6. 从确认库存和食谱模板中筛选可行方案。
7. 验证过敏原、食材可用量和营养误差。
8. 创建一周饮食计划版本并等待用户确认。

### 5.2 食材拍照

1. 图片上传私有云存储。
2. 服务端视觉 Provider 返回候选食材。
3. 用户确认食材名称、生熟状态和数量。
4. 标准化名称并关联营养记录。
5. 保存库存；原图默认 24 小时内清理。

视觉结果不直接成为事实，照片也不能可靠提供精确重量。

### 5.3 训练变更

1. 创建新训练计划版本和 `TrainingPlanChanged` 事件。
2. 根据生效日期找出受影响的未来日期。
3. 重算训练消耗和营养目标。
4. 为未锁定餐单生成替代版本。
5. 对已锁定餐单生成差异，不自动覆盖。
6. 完整成功后切换有效计划；失败时保留旧计划。

### 5.4 有限对话修改

“把鸡胸肉换成牛肉”先解析为 `replace_meal` 命令。领域服务检查过敏原、库存、营养误差和版本冲突，通过后创建新餐单版本；模型只解释结果。

## 6. 计算设计

当前策略版本为 `calculation-policy-v2`，执行顺序如下：

1. 先校验年龄 18–45 岁、BMI `18.5–<24.0`、最小化健康排除项及全部必需输入。不满足时返回 `unsupported_for_personalized_energy`，不静默切换公式。
2. 在适用范围内估算基础代谢：`BMR = 14.52 × 体重kg - 155.88 × S + 565.79`，男性 `S=0`、女性 `S=1`。该公式仅在中国正常体重成年人研究范围内使用，界面显示“初始估算”和来源，不显示“精准值”。
3. 非训练 PAL 只包含工作、通勤和家务，不包含显式训练；轻、中、重分别取 `1.50`、`1.75`、`2.00`。非训练基线消耗为 `BMR × PAL`。
4. 训练净消耗使用 `(MET - 1) × 3.5 × kg / 200 × 分钟`。MET 只能来自经审核的 2024 Adult Compendium 会话类别；力量训练组次只辅助判断有效时长和强度，不产生单动作“精确消耗”。
5. 估算维持消耗为非训练基线加当日计划训练净消耗。计划改变时使用 `Σ新计划净训练消耗 - Σ旧计划净训练消耗` 更新未来日期；只移动训练日时整周总量不变。
6. 维持、减脂、增肌初始调整分别为 `0%`、`-10%`、`+5%`。MVP 不自动扩大能量盈亏；体重趋势只触发复核提示。
7. 减脂目标不得使 BMI 低于 `18.5`。若有可用体重记录且每周下降超过 `0.5 kg`、增肌期每周增长超过当前体重的 `0.5%`，或即将越过范围门禁，停止继续调整。
8. 无训练时蛋白质使用成年人 RNI：男性 `65 g/日`、女性 `55 g/日`；一般运动/耐力训练使用 `1.4 g/kg/日`；规律抗阻训练或增肌使用 `1.6 g/kg/日`；MVP 自动上限为 `2.0 g/kg/日`。
9. 脂肪以 `25%E` 为中点并限制在 `20%–30%E`，饱和脂肪 `<10%E`；碳水必须同时满足 `50%–65%E` 和至少 `120 g/日`；膳食纤维 `25–30 g/日`，添加糖 `<10%E`。
10. 约束求解还必须包含食物多样性、过敏原、忌口和食材可用量。无法同时满足时返回 `nutrition_constraints_infeasible` 及冲突原因，不输出拼凑数值。

策略对象至少保存 `policyVersion`、`sourceIds`、`applicableAgeRange`、`applicableBmiRange`、`effectiveDate` 和 `reviewedAt`。公式、常量和 MET 映射不得散落在提示词或页面中；修改策略只影响新计划，不改写历史结果。

## 7. 数据与版本设计

身体档案、目标、训练计划、每日营养目标、餐单和计算策略都使用不可变版本。用户实际完成记录是事件事实，不因重新规划而覆盖。

每日营养目标必须引用身体档案、目标、训练计划和策略版本。重算任务使用事件 ID 作为幂等键。旧计划只在新版本完整成功且用户确认后失效。

会话记忆采用最近 12 条消息加结构化摘要；长期偏好从数据库读取。用户健康状态不得进入公共知识库或跨用户向量记忆。

## 8. 外部数据选择

- TianAPI 作为 MVP 营养查询候选，数据标准化并缓存；商业上线前完成来源、授权、缓存和 SLA 审核。
- 混元视觉作为食材候选识别首选；失败时手动录入，后续可增加百度识别适配器。
- 经典动作库在仓库中自建并版本化，避免不稳定 API 和媒体授权风险。
- 热量计算不使用外部黑盒 API。
- 中国居民 DRIs、膳食指南和 2024 Adult Compendium 作为规则研究来源；导入内容前检查商业使用许可。
- 数值证据登记采用 README 中的来源 ID；每条生产营养/MET 数据保留原始单位、食物状态或活动类别、来源版本和人工审核时间。
- 科学来源优先级为中国现行标准和正式 DRIs、系统综述/荟萃分析、专业组织共识、适用人群明确的原始研究；博客、营销材料、模型回答和供应商文案不能作为数值依据。

## 9. 异常处理

- 模型不可用不影响结构化录入、计算和已生成计划。
- 视觉不可用时回退手动录入。
- 营养 API 不可用时使用已审核缓存；无可靠数据则不生成虚假数值。
- 重算失败保持旧计划有效并允许重试。
- 并发修改通过预期版本拒绝覆盖。
- 无可行食谱时说明缺口，不放宽过敏原。

## 10. 安全与合规

只服务自述健康的成年人并最小化收集数据；不保存详细病史，只保存个性化能量门禁所需的最小化排除项确认及版本。身体档案、目标和照片默认私有；API 密钥只在服务端。产品提供告知、同意、更正、导出和删除设计，日志不保存原图和完整健康数据。

公开上线前核查微信小程序隐私要求、个人信息保护、生成式 AI 应用登记、模型备案公示和 AI 内容标识。产品明确标注非医疗用途，并对疾病、伤病、进食障碍和极端目标停止建议。

## 11. 测试设计

- 年龄/BMI/健康排除项范围门禁、计算公式、单位、舍入和策略版本测试。
- BMR 来源与性别编码、PAL 排除显式训练、MET 来源完整性测试。
- 能量目标默认值、体重速度停止条件和禁止自动扩大盈亏测试。
- 蛋白质分支、宏量营养素/纤维约束及无可行解测试。
- 训练变更影响范围、幂等和回滚测试。
- 食谱营养复算与过敏原属性测试。
- Provider 契约、超时和降级测试。
- 图片确认门禁测试。
- 用户隔离和越权测试。
- 从首次规划到变更联动的端到端测试。

测试使用固定供应商桩数据，常规测试不调用实时付费接口。

## 12. MVP 验收标准

1. 用户可以完成身体档案、目标和一周训练计划录入。
2. 系统为每天生成可追溯的能量和宏量营养素目标。
3. 食材照片只产生待确认候选，确认后才能参与推荐。
4. 食谱克数和营养汇总能够由结构化数据复算。
5. 过敏原在任何情况下都不会被放宽。
6. 移动、取消或改变一个训练日后，相关未来日期的饮食同步变化。
7. 无关日期、过去事实和用户锁定餐单不被静默改写。
8. 模型、视觉或营养 API 失败时存在可用降级路径。
9. 不支持的人群不会收到自动减脂或增肌热量，也不会静默切换公式。
10. 每个能量和营养结果能够追溯策略版本、来源 ID 和适用范围。
11. 只移动训练日时整周训练净消耗保持不变；改变时长或强度时相应未来营养目标随净消耗差值变化。
12. 营养约束无解或来源链断裂时返回明确错误，不生成模型补齐或拼凑数值。

## 13. 评审后下一步

设计已确认。实施计划从领域模型、`calculation-policy-v2`、来源登记、版本语义和测试夹具开始；只有这些确定性基础通过范围门禁、公式、约束无解和计划联动测试后，才接入 CloudBase、LangGraph 和外部供应商。
